# PHYSOGE — правила работы с проектом

## Базовая ветка разработки

Рабочая ветка:
`feature/physoge`

Не изменять `main` напрямую.

Не выполнять merge в `main` без отдельного прямого указания пользователя.

Не создавать Pull Request в `main` без отдельного указания пользователя.

Если Codex создаёт временную ветку вида `codex/...`, `*-codex/...` или аналогичную, Pull Request по умолчанию должен быть направлен в `feature/physoge`, а не в `main`.

## Реальная архитектура PHYSOGE

Проект сейчас является статическим сайтом без обнаруженной Node/npm build-системы.

Основные части репозитория:

- `index.html` — главный файл сайта; в нём сосредоточена основная разметка интерфейса, стили и JavaScript-логика приложения.
- `images/` — основная директория изображений, учебных карточек, теории, схем и других медиафайлов.
- `ege-physics/` — материалы курса ЕГЭ по физике; внутри отдельных уроков есть каталоги `task-solutions/` с изображениями решений задач.
- `sources/` — дополнительные исходные материалы проекта.
- `hero-physics.svg` и отдельные изображения в корне — статические медиафайлы сайта.
- `.github/workflows/deploy.yml` — существующий GitHub Actions workflow деплоя на Zomro через SSH/rsync.

На момент создания этого файла в корне не обнаружен `package.json`, поэтому нельзя предполагать наличие npm-команд, отдельного bundler, framework build pipeline, lint или test runner, пока они фактически не появятся в репозитории.

Текущий deploy workflow запускается для push в `main`, `master` и `work`. Ветка `feature/physoge` не должна добавляться в боевой deploy без отдельного прямого указания пользователя.

## Работа с существующим кодом

1. Перед изменением сначала найти существующую реализацию.
2. Предпочитать минимальные локальные изменения.
3. Не переписывать крупные рабочие блоки без необходимости.
4. Не удалять существующий функционал без прямого указания пользователя.
5. Не создавать дубли функций, компонентов, CSS или другой логики, если можно изменить существующую реализацию.
6. Не изменять несвязанные с задачей части проекта.
7. Сохранять существующую архитектуру и используемый стек.
8. Не добавлять новые фреймворки, библиотеки, зависимости или build-инструменты без прямого указания пользователя.
9. Не менять существующие форматы данных, настройки и хранилища без необходимости.
10. При неоднозначной задаче сначала определить область изменения и избегать масштабной переработки.
11. Особенно осторожно работать с большим `index.html`: сначала найти точный существующий блок, функцию, данные урока или стили, затем менять только необходимый участок.
12. Не удалять и не переименовывать изображения, пути к решениям задач, учебные карточки, анимации, симуляторы, уроки или разделы курса без прямого указания пользователя.
13. Перед изменением путей к изображениям сначала проверить фактический путь файла в репозитории.
14. Не изменять `.github/workflows/deploy.yml`, секреты, схему деплоя или список deploy-веток без отдельного прямого указания пользователя.

## Проверка после изменений

После каждой задачи:

1. Проверить синтаксис изменённых файлов.
2. Использовать существующие тесты/lint/build, если они уже есть в проекте.
3. Если специальных тестов/lint/build нет, выполнить доступные локальные проверки, соответствующие изменению, и явно указать их ограничения.
4. Проверить `git diff`.
5. Убедиться, что случайно не изменены посторонние файлы.
6. Для изменений `index.html` отдельно проверить, что основной JavaScript не содержит синтаксических ошибок и что изменение не ломает существующую навигацию и учебные элементы, связанные с задачей.
7. Для изменений изображений/каруселей проверить фактические относительные пути и отсутствие очевидных 404-ссылок.
8. Сообщить:
   - что изменено;
   - где изменено;
   - какие проверки выполнены;
   - какие файлы изменены.
9. Не выполнять merge в `main` самостоятельно.

## Правило Pull Request

Если работа выполнена во временной ветке Codex, целевая схема по умолчанию:

`codex/...` → `feature/physoge`

Не:

`codex/...` → `main`

Перенос изменений из `feature/physoge` в `main` выполняется только после отдельного решения пользователя.
